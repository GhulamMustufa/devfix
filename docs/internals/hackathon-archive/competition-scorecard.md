# Micro1 Hackathon - Engineering Scorecard

This scorecard translates the official 100-point rubric into actionable engineering and project management tasks.

## 1. Problem & User Value (15 Points)
**What the judge is looking for:** A clearly defined user with a meaningful bottleneck that actually matters.
**Evidence needed:** 
- A clear description of the user.
- Explanation of the bottleneck.
- Why solving it is valuable in practice.
**Engineering Decisions to Improve Score:** 
- Focus on a specific, narrow problem rather than a generic "assistant".
- Ensure the problem is grounded in a real-world workflow.
**Mistakes that reduce score:** 
- Vague user persona.
- Solving a non-existent or trivial bottleneck.

## 2. Agent Solution & Engineering (30 Points)
**What the judge is looking for:** Purposeful use of agents and technically sound implementation.
**Evidence needed:** 
- Code that uses context, tools, memory, verification, skills, or orchestration *only when necessary*.
- Explanations of *why* each design choice was made and how it solved the problem.
**Engineering Decisions to Improve Score:** 
- Justify every agent component. 
- Keep the architecture as simple as possible to achieve the goal reliably.
**Mistakes that reduce score:** 
- Over-engineering (e.g., adding 5 agents when 1 would do).
- Adding components without a clear, measurable benefit.

## 3. End to End Quality (20 Points)
**What the judge is looking for:** A realistic, self-contained execution that produces a polished, usable final result.
**Evidence needed:** 
- The final output generated by the agent.
- A workflow that completes from start to finish without awkward manual interventions (unless explicitly designed as a human checkpoint).
**Engineering Decisions to Improve Score:** 
- Format the output nicely (e.g., structured reports, clean code, proper summaries).
- Ensure the result does not look like a generic "ChatGPT" draft.
**Mistakes that reduce score:** 
- Output that requires heavy manual editing to be usable.
- "Obvious AI-generated draft" tone.

## 4. Measured Improvement (15 Points)
**What the judge is looking for:** Proof that your solution is better than a reasonable baseline.
**Evidence needed:** 
- A simple baseline implementation.
- The same evaluation cases run on both baseline and agent.
- A changelog connecting iterations to evidence.
**Engineering Decisions to Improve Score:** 
- Build a solid, fair baseline (don't "sandbag" it).
- Automate the evaluation of the 10+ cases to prove consistency.
- Document every iteration, including failures, in the changelog.
**Mistakes that reduce score:** 
- Unfair baseline comparison.
- Missing changelog entries.
- Claims of improvement without evidence.

## 5. Reproducibility (15 Points)
**What the judge is looking for:** The ability to run your project and get the same results from a clean environment.
**Evidence needed:** 
- A comprehensive Reproduction Guide (setup, commands, data, expected output, versions, runtime, cost).
- Access to the required data (public/synthetic/anonymous).
**Engineering Decisions to Improve Score:** 
- Provide a `requirements.txt` or `package.json`.
- Script the setup process if possible.
- Avoid hardcoded local paths or relying on private credentials.
**Mistakes that reduce score:** 
- Missing setup instructions.
- Code that only runs on the creator's machine.
- Requiring private data the judges cannot access.

## 6. Hot Take / Insights (5 Points)
**What the judge is looking for:** A practical lesson learned from a failure mode.
**Evidence needed:** 
- An entry in the deliverables documenting a failure mode and the resulting insight.
**Engineering Decisions to Improve Score:** 
- Actively look for edge cases where the agent fails.
- Document a removed experiment that failed and explain *why* it failed in the context of building reliable agents.
**Mistakes that reduce score:** 
- Ignoring failures.
- Providing a generic observation instead of a practical lesson.
